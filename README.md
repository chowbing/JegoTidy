| 改动 | 为什么 |
|---|---|
| 四个类名进"已知广告位"白名单 → 隐藏 | 直接目标 |
| **新增收起机制（第 12c-2 节）** | **隐藏 ≠ 去掉**。`hidden=YES` 只是不画，布局里那一格还在。「我的」页那条在最后一格（留白在底部，尚可忍），「电话/消息」页那条在**页面中部**，留白一眼就看得出来 |

**收起机制按"侵入性从小到大"试四条路，第一条成功就停：**

| # | 路径 | 前提 | 会真正重排吗 |
|---|---|---|---|
| ① | 视图自身高度约束 → `constant = 0` | 有约束 | 会 |
| ② | 父视图上定死它高度的约束 → `constant = 0` | 有约束 | 会 |
| ③ | `contentView` 高度约束 → `constant = 0` | 自撑高 cell | 会 |
| ④ | 给**这个 cell 类**加一份 `preferredLayoutAttributesFittingAttributes:` 覆写，返回高度 0 | 布局走自撑高（`estimatedItemSize` 非零） | 会 |

全失败 → **如实记「会留白」**，不假装成功。

> ★ **④ 用「类名」认身份，不是记 `indexPath`。**
> `indexPath` 是**位置**；用位置认身份，列表顺序一变就会改到无辜的格子 ——
> 这正是本项目 v0.3 踩过的那个坑（"用位置认身份，自己一改位置就自毁"，见第 6 节）。
> 类名稳定，而且我们本来就只认这几个类。**同一个坑不踩第二次。**
>
> ★ **④ 用 `class_addMethod` 而不是 `method_setImplementation`。**
> `TBMineBannerCell` **没有自己实现**这个方法，是从 `UICollectionViewCell` 继承来的；
> 继承来的 `Method` 属于父类，`method_setImplementation` 一改就波及全 App 每一个 cell。
> 用 `class_addMethod` 在**子类上新增一份**，只在子类生效。

> ★ **每一步都有自证**：收起之后 1.5 秒回看实际高度，日志里会有
> `[广告收起·自证] … 高度已为 0，收起生效` 或 `… 高度仍为 N —— **收起未生效**`。
> **声明不是证据** —— "覆写已加"不等于"覆写被调用过"（不是自撑高布局就永远不会被调用）。

### v0.3.4 真机结果（2026-09-30，v1.0 的依据）

| 位置 | 结果 |
|---|---|
| 「我的」页底部广告 | ✅ **已清掉**（用户确认） |
| 「电话/消息」页中部横幅 | ❌ **还在** |

但这一版留下的**日志证据链**直接定位了原因：

```
[广告清理·页面出现] 隐藏 2 个（本次新命中类：BannerCycleView, BannerCycleViewCell）
[广告收起·页面出现] BannerCycleView     → ①自身高度约束→0（原 145）          ← 当时确实收掉了
[广告收起·自证]     BannerCycleView     1.5s 后高度已为 0，收起生效
[广告清理·定时]     隐藏 1 个（本次新命中类：TBMineBannerCell）
[广告收起·定时]     BannerCycleView     → 无可用高度约束、也不是 frame 布局   ← 它又出现了
[广告收起·自证]     BannerCycleViewCell 1.5s 后高度仍为 145 —— **收起未生效**
[广告收起·自证]     TBMineBannerCell    1.5s 后高度仍为 155 —— **收起未生效**
```

**第三行是决定性的**：收起只在我们**刚刚隐藏它**时才会被调用 →
那一轮 `BannerCycleView` 一定是 `hidden = NO` → **App 把隐藏过的广告重新显示回来了。**

结论：`hidden = YES` 不是一劳永逸的。靠 1 秒一次的扫掠去追是**竞速** ——
追得上也难看（用户看到的仍是广告），追不上就是现在这样。

| # | 改动 | 为什么 |
|---|---|---|
| 1 | **新增「粘性隐藏」（第 12c-3 节）** | 把规则从"1 秒追一次"**下沉到类**：给白名单里的类加 `layoutSubviews` / `setHidden:` 两份覆写 |
| 2 | 修掉 ③ 的**排他**逻辑 | 原来 `contentView` 约束一改成功就 `return`，导致 ④ 永远没机会装。实测 ③"改成功"≠"生效"（`BannerCycleViewCell` 高度仍是 145）→ 现在 ③④ **并行** |
| 3 | 修正诊断 | 约束**已经是 0** 时不再误报"无可用高度约束" —— 那会把"上一轮已收起"误判成"收不了"，正是上面那条被掩盖的原因 |
| 4 | 后悔药扩展到类级覆写 | 长按 T 现在会同时撤销 ④ 的自撑高覆写和粘性隐藏的两份覆写 |

**粘性隐藏的两个覆写：**

| 覆写 | 作用 | 兜住的情况 |
|---|---|---|
| `layoutSubviews` | 每个布局周期重新断言 `hidden = YES` | 新建 / 复用出来的 cell 默认不隐藏 |
| `setHidden:` | App 把它设回 `NO` 的**那一刻**压回去 | App 显式重新显示 |

两条路互补，任一条装上就有粘性；两条都装不上（App 自己实现了同名方法）就**如实记日志**
（`[广告粘性·…] … App 自己实现，跳过`），不假装成功。

> ★★ **父实现必须"按类各存一份"，不能用一个全局。**
> 白名单里 4 个是 `UICollectionViewCell` 子类，它们实际继承的 `layoutSubviews`
> **来自 `UICollectionViewCell` 而不是 `UIView`**。若统一取 `[UIView layoutSubviews]` 的 IMP
> 去转发，就会**绕过 `UICollectionViewCell` 自己的布局逻辑** —— cell 会画错。
> 所以安装时用 `JTSafeInstanceMethod(类, sel)` 取"真正会被调用的那份"，存进以**类指针**为键的字典。
> ④ 的自撑高覆写原本也有同一个隐患，v1.0 一并改掉（见第 3c 节的通用回查 `JTBaseIMPForOwner`）。
>
> ★ **停手开关必须在覆写内部检查**：长按 T 后 `gJTAdRuleDisabled = YES`，覆写立刻变直通。
> 否则"恢复"会被自己的覆写压回去 —— 用户看到的是"按了没反应"。
> `JTRestoreAds` 也确实是**先置位、后恢复**，顺序不能反。

### v1.1 做了什么 —— 把留白收掉（第 12c-4 节）

Shawn 真机反馈：**"图片没有了，但图片所在位置留下了空白。"**
这正是 v0.3.4 就记录在案的"收起未生效"：隐藏成功，但**布局里那一格还在**。

**为什么 ①②③④ 都收不掉**（v0.3.4 的日志已经给了答案）：

```
内容侧：BannerCycleView 高度已为 0，收起生效        ← 内容真的收掉了
格子侧：BannerCycleViewCell 高度仍为 145            ← 格子没动
```

内容收到 0、cell 还是 145 → **cell 的高度不是内容给的，是布局对象给的**。

| 机制 | 为什么无效 |
|---|---|
| ①②③（自身 / 父视图 / contentView 的高度约束） | 改的都是**内容**的约束，管不到布局 |
| ④（`preferredLayoutAttributesFittingAttributes:`） | **只在自撑高模式下才会被调用**。固定 `itemSize` 模式下布局根本不问 cell —— 装了也是死的（"声明不是证据"的又一例） |

**唯一能重排的路：影响 `prepareLayout` 的输入。** 两个容器各有各的 API：

| 容器 | 要 hook 的方法 | 归属 |
|---|---|---|
| `UICollectionView` | `collectionView:layout:sizeForItemAtIndexPath:` | delegate |
| `UITableView` | `tableView:heightForRowAtIndexPath:` | delegate |

它给的尺寸既决定这一格的 frame，也决定**后面所有格的起点** —— 改它才会真正重排。

**三个关键决策**（每一条都对应一个会让事情变坏的方式）：

| 决策 | 不这么做会怎样 |
|---|---|
| **返回 0.5pt，不是 0** | 高度 0 的 item 是**空矩形** → `CGRectIntersectsRect` 返回 NO → 退出可见集 → cell 被回收 → `cellForItemAtIndexPath:` 返回 nil → **我们认不出它了**（识别依赖那个 cell 的类名）→ 0/145 来回抖 = 屏幕上看就是**闪** |
| **认身份仍用类名；"记下 indexPath"由真实 cell 提供，且实时 cell 优先** | 布局阶段（`prepareLayout`）cell 可能还没建 / 已滚出可见区，`cellForItemAtIndexPath:` 常返回 nil → 纯靠它识别会**静默失效**。所以扫掠时（手里正拿着那个 cell）把 `容器 → indexPath` 记下来兜底；只要实时 cell 拿得到就用实时答案，且实时答案说"这里不是广告"时**顺手删掉记录**（自愈）。**从不猜任何位置** —— 与 Gotcha 25 的区别就在这 |
| **加钩子前先自证"布局确实按固定尺寸定高"** | 拿 cell 实际尺寸和 `fl.itemSize` / `tv.rowHeight` 比，对不上说明高度另有来源（自定义布局 / 自撑高）→ 加钩子会**改变整个列表的布局行为**。宁可留白也不冒险，如实记 `**不敢加**：…` |

另外两处细节：

- **`invalidateLayout` 必须节流**（同一个容器 0.5s 一次、全局上限 20 次）——
  我们自己也在动布局，不节流会出现"invalidate → 布局 → 又 invalidate"的抖动。
  表格没有 `invalidateLayout`，用 `beginUpdates` / `endUpdates` 强制重问行高。
- **后悔药必须能撤销"加在类上的方法"**：`class_addMethod` 上去的那批不能删（运行时不支持），
  长按 T 时换成"永远返回原尺寸"的**直通版**。不做这一步的话，恢复广告后它会被布局压成 0.5pt
  —— 比不恢复更怪。

**v1.1 新增的日志**（都是自证行，不是"我做了 X"的声明）：

```
[广告item·页面出现] BannerCycleViewCell → 换掉 XxxViewController 自己的实现（转发给原实现）
[广告item·自证]     BannerCycleViewCell 布局层已收起：0.5pt、与下一格间距 0.0pt ✅（size 钩子共被调用 37 次、行高钩子 0 次）
```

第三种结局要特别注意，它把"没被问"和"问了没用"分开了：

```
[广告item·自证] X 仍是 145pt —— **布局层没收到**
                （size 钩子共被调用 0 次、行高钩子 0 次；没被问 = 钩子没生效，被问了还这样 = 高度另有来源）
```

## 1. 为什么 v0.2 先做"探针"而不是直接写规则

要"移除 tab"，得先知道 **tab 是怎么被建出来的**。无忧行是原生 + H5 混合的国产 App，
它的 tab bar 有两种可能，**改法完全不同**：

| 情况 | 改法 | 需要知道什么 |
|---|---|---|
| 系统 `UITabBarController` | 拦 `setViewControllers:`，过滤掉目标 VC | 哪个类、VC 数组长什么样、tab 标题对应哪个类 |
| 自绘容器（国产 App 常见） | 找到容器类，隐藏对应 tab 按钮 + 从内容区摘掉对应子 VC | 容器类名、tab 按钮的类名/文案、内容区的结构 |

猜错就是白跑一轮构建。所以这一版**不做任何修改**，只把"tab 是怎么建出来的"变成**直接证据**。

同类项目的实测教训：
**"改一个变量看 App 有没有反应"每轮只能排除一个假设，几十轮都收敛不了**；
而 dump 一次真实结构是直接证据，一轮就能定规则。

| 轮次 | 产出 | 目的 |
|---|---|---|
| v0.2 | 探针 dylib | 抓 tab 构造过程 + 弹窗/开屏 + 视图树（**已完成**，见第 5 节结论） |
| v0.3 | 规则 dylib | 按实测 tag 移除 tab、清已确认的广告位、拦开屏/启动弹窗（**目标 ① 已收官**） |
| v0.3.3 / v0.3.4 | 取证升级 + 收起占位 | 把 dump 升级成"能直接指向广告位"；隐藏之后把占的高度收掉 |
| **v1.0** | **最终版** | 广告规则**下沉到类**（粘性隐藏），不再被 App 重新显示；③④ 并行；诊断不再误报 |
| （未做） | 后续可选 | 补白名单（靠日志里"可疑但未处理"的类名）、H5 页注入 CSS、delegate 的 size 钩子收留白 |

## 2. 环境与工具链

- 本机 **Windows，无 macOS** → 编译走 GitHub Actions（`macos-latest` runner）。
- 本机 **无 Xcode / 无 Theos** → 本地只做静态审计，不做编译。
- 真机注入：**TrollStore + TrollFools**（选 App → 注入 dylib → 重启生效）。

```bash
# 推送前必跑（本机即可执行）
C:/Users/1107089/.workbuddy-ai/binaries/python/versions/3.13.12/python.exe tools/preflight.py Tweak.xm
```

| 脚本 | 抓什么 |
|---|---|
| `chk.py` | 括号/引号不配对（tokenizer 感知，字符串里的 `}` 不会骗过它） |
| `audit.py` | A 调用点早于定义 · B 全局变量引用早于定义 · C 递归 block 缺 `__block` |
| `strchk.py` | 字符串字面量未闭合 |
| `objcpp.py` | ObjC++ / ARC 专属硬错误：A 函数指针→`void *` · B out `id *` 参数 · C 三元混 `nil`（仅提示） · D `volatile` 被丢弃 · **E 标量→对象指针强转（ARC 禁止）** |
| `ips.py` | 崩溃报告解析（`python tools/ips.py crash.ips`） |

**为什么必须跑**：`.xm` 被 clang 当 **Objective-C++** 编译，隐式函数声明、类型不匹配、
`IMP` 隐式转 `void *` 全是**硬 error**，`-Wno-error` 救不了。本机编译不了，
一次推送 = 一轮 Actions，所以本地先把这类错误清掉。

> ★★ **检查器本身也要自证。** `preflight.py` 第 0 步会拿一份**故意写坏**的样本喂给每个检查器，
> **必须报错才算通过**，然后再跑真文件。理由：一个对坏文件也说 OK 的检查器比没有更糟 ——
> 它给的是**虚假信心**。
>
> 规则 E 就是这么补上的：2026-09-30 v1.0 推送时 preflight **四项全过**，
> 但 CI 报了 `error: cast of 'uintptr_t' to 'Class' is disallowed with ARC`
> —— 说明检查器有盲区。补规则的同时必须**补一份对应的坏样本**，
> 否则下次还是漏。**每加一条规则，就加一条自证样本。**

### dump 里怎么看广告（v0.3.3 加的字段 + v0.3.4 补的布局取证）

| 字段 | 样子 | 怎么用 |
|---|---|---|
| **窗口坐标** | `win=(0,724,430,80)` | 每个节点都带。屏幕高度 932 的话，`win.y=724` 就是屏幕下部 —— 直接和截图对位置，不用自己把父链 origin 加一遍 |
| **已知广告位** | `★★已知广告位` | 命中了实测确认的白名单（`TripOperatingAdCell` / `JegoSuspendedADView` / `TBMineBannerCell` / `TBMineBannerItemCell` / `BannerCycleView` / `BannerCycleViewCell`） |
| **广告嫌疑** | `★广告嫌疑` | 类名命中了窄词表（`Advert`/`Banner`/`Promo`/`Market`/`Splash`…）。**只是嫌疑，不等于要删** |
| **H5 标记** | `[H5]` | 节点在 `WKWebView` 里。**出现这个标记基本可以停手** —— 原生方案对 H5 内部元素无效，得走注入 CSS |
| **布局取证** | `自身高度约束=… fitting方法=继承 itemSize=(…) estimatedItemSize=(…) 自撑高=是/否` | v0.3.4 新增，只挂在广告节点下。**它直接决定收起走哪条路**：`自撑高=否` 或 `非 FlowLayout` → ④那条路不适用，得换 size 钩子 |
| **广告候选汇总** | `--- 广告候选汇总（当前页 JegoMineViewController）` | 单独一段，只列"已知广告类 / 类名可疑 / 横幅形态图片视图"三类，**带窗口坐标**。零命中时会给一句明确的排查方向 |

> 汇总段**只报告、不隐藏**。类名关键词误报率高（`Banner` 可能只是正常轮播图），
> 拿它直接去藏视图，就是把"猜"写进了产品行为里。判定由人做，改由下一版做。

### 如果删错了 / 界面不对

**发布版**：在 **TrollFools 里关掉这个插件的注入** —— App 立刻完全回到原版，不用重新构建/重装。
比"长按 T"更彻底（T 只恢复本次启动）。

**调试版**：长按橙色 T 立刻恢复（tab + 广告 + 三类类级覆写一起），恢复后本次启动内规则不再生效。

想看"到底哪条规则做了什么"，就把 `ENABLE_DEBUG_UI` 改成 `1` 重新构建，然后长按 JT 取诊断 —— 里面会有：

- `[tab规则] 已留底：5 个 tab，selectedIndex=N，将移除下标 {…}。现有：1000:… 1001:… …`
  —— 这是"tag ↔ 页面类"的实测对应表
- `[tab自绘] 已绑定槽位（槽宽 86.0）：槽0(1 个): … 槽1(1 个): …` —— **最该看的一行**：
  它说明 5 个槽位各绑到了哪些视图。**没有这一行 = 绑定失败，自绘层整个没动**
- `[tab自绘·结果·…]` —— 每个槽位的**最终状态**（类名 + 显/隐 + 内含文字 + x）。
  **判定标准：被移除的槽位应全是 `·隐`，保留的槽位应全是 `·显` 且 x 均分**
- `[tab自绘] 绑定失败：只认到 N/5 个槽位…` —— 出现这行说明我们放弃了自绘层，把这段发我
- `[广告清理·…] 隐藏 N 个（本次新命中类：…）` / `可疑但**未处理**的类：…` —— 后者是下一轮的白名单来源
- `[广告粘性·…] 规则已下沉到类（BannerCycleView → layoutSubviews:已加 | setHidden:已加）`
  —— ★ **v1.0 新增，最该看的一行**。`已加` = 粘性生效；`App 自己实现，跳过` = 这条覆写装不上，
  只能靠定时扫掠追
- `[广告收起·…] 收高度的结果：XXX → …` —— 说明用了四条路里的哪一条
  （`**已是 0**` = 上一轮已收起，不是收不了）
- `[广告收起·自证] … 1.5s 后高度已为 0，收起生效` / `… **收起未生效**` —— **自证行**

  （`换掉 XxxViewController 自己的实现` = 委托本来就有，我们插了一层；
   `给 Xxx 加上` = 委托没有，我们加的；`**不敢加**：cell 尺寸 N ≠ itemSize M` = 自证没过，**故意不动**；
   `不在列表 cell 里，不适用` = 它不在任何列表里，如悬浮广告）
- `[广告item·自证] … 布局层已收起：0.5pt、与下一格间距 0.0pt ✅（size 钩子共被调用 N 次…）`

## 6. 安全设计（每一条都对应上一轮踩过的坑）

| 机制 | 防的是什么 |
|---|---|
| `%ctor` 只装崩溃处理器，其余全部 `dispatch_async` 到主队列 | 主队列在 `UIApplicationMain` 起 runloop 前**根本不执行**，这是"绝对晚于启动"的结构性保证，比 sleep 秒数可靠 |
| 查类表用 `class_copyMethodList` 手走父类链，**绝不用** `class_getInstanceMethod` | 后者会强制 `+initialize`；dyld 阶段全进程扫类 = 把 App 几百个类挨个初始化一遍，任一类的 `+initialize` 抛异常就死在启动前，且 `@try/@catch` 救不了（异常在 `dispatch_once` 里被 libdispatch 边界吞掉变成 `std::terminate`） |
| 启动自愈计数（同构建连续 3 次启动异常 → 只留按钮不装钩子） | 防"崩到 App 完全打不开、连诊断都拿不到"。换构建 token 自动从 0 开始，修好即恢复 |
| 诊断缓冲滚动窗口 + 显式截断标记 | 防"写满就静默停止"——那会保留头部丢掉尾部；标记是为了让"只有这些条目"和"只剩这些条目"可区分 |
| **一个 selector 只挂一个类**（原 IMP 是单个全局，不是字典） | **2026-09-30 栈溢出闪退的根因**。让一个共享 shim 服务多个类，转发就只能靠"从对象类沿父类链找第一份原 IMP"，而它**无法区分直接调用和 `[super]` 调用** → UIKit 的 `[super viewDidAppear:]` 又回到我们的 shim，查表又命中同一个类 → 无限递归爆栈。详见 `Tweak.xm` 里 `JTInstallSingleHook` 上方的完整崩溃栈 |
| 安装器**幂等**（`method_getImplementation(own) == replacement` 就拒绝） | 二次安装时 `method_setImplementation` 返回的是**我们自己的 shim** → "原 IMP"变成自己 → 一调用就自递归 |
| **两个 `setViewControllers:` 重载各用独立原 IMP** | 共用一个按类名索引的字典会互相覆盖 → 转发到错误的 IMP → 参数个数对不上 + 对方也是我们的 hook → 无限递归 |
| 信号处理器注册 `sigaltstack` + `SA_ONSTACK` | 栈溢出（最常见的崩溃类型）时，处理器默认跑在**已经耗尽的那条栈**上，第一条指令就二次 SIGSEGV —— 于是 `wf_crash.log` 一个字节都写不出来。必须换独立栈，且 `signal()` 设不了 `SA_ONSTACK`，得用 `sigaction()` |
| `JTIsDescendantOf` 廉价预筛 | 类名扫描时避免为全进程几万个类各做一次 `class_copyMethodList` |
| 弹窗取调用栈前先查"是不是新键" | `callStackSymbols` 要符号化，不便宜；present 可能被系统高频调用 |
| 类名扫描放后台队列 | 几万个类跑正则，放主线程会有可见卡顿；这些只读运行时查询天然线程安全 |
| `UIWindow addSubview:` 用 `class_addMethod` 加**自己的**实现 | 直接 `method_setImplementation` 改的是从 UIView 继承来的那份，会波及全 App 每一个 UIView |
| 反查 selector 归属带对照组 | 全进程扫描会返回"对任何 selector 都回答 yes"的万能类，实测同一批五个类能"实现"十几个毫不相关的 selector |
| 信号处理函数里只用 `open/write/snprintf/backtrace_*` | 这些是异步信号安全的；碰 `NSString`/`NSLog` 会分配内存导致二次崩溃 |

### v0.3 新增的三条"改界面"安全线

| 机制 | 防的是什么 |
|---|---|
| 保留 tag **一个都没匹配上** → 整体放弃并大声记日志 | App 改了 tag 时，**绝不猜一个删掉**，更**绝不把 tab 清空**（清空 = 白屏） |
| 保留集 ≥ 全集 → 什么都不做 | 无可移除时不误动 |
| 自绘图标数 ≠ 预期槽位数 → **不猜**，只记日志 | 槽位是"第 k 个 ↔ 第 k 个 tab"的**位置约定**，数量一变约定就不成立；硬套只会把图标藏错地方 |
| **槽位绑定只做一次**（在原始布局下建立 `槽位 → [视图]`，之后永不按 x 重新推断） | ★ **v0.3 首轮真机踩到的坑**：用位置认身份，一旦自己改过位置就自毁 —— 重排一次后排序结果不再等于原始槽位顺序，于是藏错、来回翻，最后图标叠在一起。见第 1 节的"v0.3 首轮真机结果" |
| 所有改动**幂等**（状态对了就一个字节都不改） | 会被定时复检 / `viewDidAppear` / 手动按钮反复调用；非幂等会和 App 自己的重排互相打架，屏幕闪烁 |
| `viewDidAppear` 里改 tab bar 前先 `dispatch_async` 一跳 | 不在 UIKit 的转场中途改容器结构 |
| 广告白名单**只收实测确认的类**，泛匹配只记日志 | 关键词泛匹配（Ad/Banner/Market…）会误伤正常业务视图；**误伤比漏清难查得多**（漏清少个广告，误伤是功能没了） |
| 弹窗拦截**先让它真的弹出来、再收掉**，而不是"不转发" | 不转发会让调用方在 completion 里推进的状态机永久卡住。代价是可能闪一帧，换来 App 状态一定自洽 |
| 弹窗判定带**业务白名单**（Login/Auth/Privacy/Agreement/Alert/Pay/WebView…） | 误拦登录/权限/协议弹窗 = 功能直接不可用 |
| 长按 T = 恢复原始 tab + 本次启动内停手 | 后悔药。同时停手是必须的 —— 复检链还在跑，不停手的话下一次复检会立刻把 tab 又删掉，用户看到的是"按了没反应" |
| 广告扫掠用 `dispatch_source` 而不是 `NSTimer` | `NSTimer` 受 runloop mode 影响：滚动 `UITableView` 时默认 mode 不跑定时器，滑动期间广告会短暂露出来 |
| 广告扫掠只在 `UIApplicationStateActive` 时跑 | 后台不必要，且往非活跃界面写 `hidden` 可能干扰 App 自己的状态恢复 |
| 每类广告只记一次日志 | App 一旦把广告重新显示出来，否则会每秒刷一行，把真正有用的信息挤出诊断缓冲 |

### v1.0 新增的三条"广告不再被重新显示"安全线

| 机制 | 防的是什么 |
|---|---|
| 覆写用 `class_addMethod` 加在**子类**上 | `layoutSubviews` / `setHidden:` 都是 `UIView` 的方法；改继承来的 `Method` 会波及全 App 每一个视图 |
| **父实现按类各存一份**（`JTBaseIMPForOwner` 通用回查），不用全局单份 | 白名单里 4 个是 `UICollectionViewCell` 子类，它们继承的 `layoutSubviews` 来自 `UICollectionViewCell` 而非 `UIView`。统一取 `[UIView …]` 的 IMP 转发会**绕过 cell 自己的布局逻辑**，把 cell 画错 |
| 父实现存进 **C 结构体定长数组**（`JTBaseIMPTable`），不用 `NSMutableDictionary` | 键是 `Class` —— 对象指针。塞进字典要 `@((uintptr_t)cls)`、取出要 `(Class)key.unsignedLongLongValue`，而后者是 **ARC 明令禁止的"整数→对象指针"强转**，直接编译失败。表项 ≤ 8 个，定长数组既不需要任何强转，也没有每轮布局的字典分配 |
| `layoutSubviews` 里**只在确实还是显示状态时才写** `hidden` | 每次布局都无条件写一遍 `hidden` 会把父视图反复标脏 → 布局循环。判一下再写，一轮就收敛 |
| 停手开关**在覆写内部**检查，且 `JTRestoreAds` **先置位、后恢复** | 顺序反了会出现"换回父实现的瞬间又被旧覆写压回 `hidden=YES`"的窗口 → 用户看到"按了没反应" |
| 撤销后**清空 base IMP 缓存和已装类名集合** | 不留下"看起来装过、实际没装"的错觉；也允许之后重新安装 |
| 两条覆写**互补**，任一装上就有粘性；都装不上就**如实记日志** | 只靠一条会有覆盖盲区；静默失败比没有更糟 |

### v0.3.4 新增的四条"收起广告"安全线

| 机制 | 防的是什么 |
|---|---|
| 收起用**类名**认身份，**不记 `indexPath`** | `indexPath` 是**位置**。用位置认身份，列表顺序一变就会改到无辜的格子 —— 与 v0.3 那个自毁 bug 是同一种错误。**同一个坑不踩第二次**（v1.1 的"记录 indexPath"与这条的区别见下一节 —— 那**不是**靠位置推断） |
| ④ 用 `class_addMethod` 加在**子类**上，不用 `method_setImplementation` | 该方法是从 `UICollectionViewCell` 继承来的；改继承来的 `Method` 会波及全 App 每一个 cell |
| App 若**自己实现**了该方法 → **不动它**，只记日志 | 要动就得为每个类各存一份原 IMP，而"一个 selector 挂多个类"正是栈溢出的成因 |
| 收起之后 **1.5s 回看实际高度**（自证行） | "覆写已加"只是**声明**，不等于"覆写被调用过"（非自撑高布局就永远不会被调用）。**声明不是证据** |
| 长按 T 除了恢复 `hidden`，还把**覆写换回父类实现** | ④ 是加在**类**上的，没法按视图撤销。不中和的话，"恢复"之后广告仍然不显示，用户看到的是"按了没反应" |

### v1.1 新增的五条"让布局层收掉那一格"安全线

| 机制 | 防的是什么 |
|---|---|
| 收成 **0.5pt 而不是 0** | 高度 0 的 item 是**空矩形**，`CGRectIntersectsRect` 返回 NO → 退出可见集 → cell 被回收 → `cellForItemAtIndexPath:` 返回 nil → **识别依据（那个 cell 的类名）没了** → 0/145 来回抖 = 屏幕上看就是闪 |
| **加钩子前先自证**：cell 实际尺寸 ≈ `fl.itemSize` / `tv.rowHeight`（±1pt） | 对不上说明高度另有来源（自定义布局 / 自撑高），这时加钩子会**改变整个列表的布局行为**。宁可留白也不冒险，如实记 `**不敢加**：…` |
| 自撑高 / 非 FlowLayout / 行高非固定值 → **一律跳过** | 那些情形下布局**不会问**我们的方法，加了也是死的（"声明不是证据"）。跳过并说明原因，比装一个没用的钩子好 |
| **`invalidateLayout` 节流**（同容器 0.5s、全局 ≤20） | 我们自己也在动布局，不节流会出现"invalidate → 布局 → 又 invalidate"的抖动 |
| `class_addMethod` 上去的那批，撤销时换成**直通版**（永远返回原尺寸） | 运行时不支持删方法。不换的话，长按 T 恢复广告后它会被布局压成 0.5pt —— **比不恢复更怪** |

> ★★ **v1.1 的"记录 indexPath"为什么不违反上一条"不记 `indexPath`"：**
> v0.3 的错误是**靠位置推断身份** —— 数第几个、按 x 排序，位置一被自己改动就自毁。
> v1.1 是**记录来自真实 cell 的事实**：扫掠时手里正拿着那个 cell，问它自己的类名、
> 问它自己在哪个 `indexPath`，把二元组存下来；布局阶段（cell 可能还没建）拿不到 cell 时用它兜底。
> 而且**永远优先信实时 cell** —— 只要 `cellForItemAtIndexPath:` 拿得到就用实时答案，
> 实时答案说"这里不是广告"时还会**顺手把记录删掉**（自愈）。
> 位置变了最多 1 秒（下一次扫掠）就纠正过来，**我们从不猜任何位置**。
> 一句话：位置是**证据**，不是**身份**。

## 7. 风险与边界

- **合规**：这是给**你自己的设备、你自己的账号、你自己安装的 App** 做界面精简，
  不绕过付费、不伪造请求、不修改服务端数据。但**仍可能违反该 App 的用户协议**，
  风险自负。不要分发改造后的 IPA。
- **越狱检测**：无忧行可能带越狱/注入检测。首次运行如果闪退或弹警告，
  把现象告诉我 —— 崩溃报告会落在 `Caches/wf_crash.log`，下次启动自动读回诊断框。
  （栈溢出一类崩溃现在也能写出来了，见第 6 节的 `sigaltstack` 一行；
  子线程崩溃仍可能写不出，那种直接抓系统 `.ips`。）
- **`viewDidAppear:` 的观测覆盖面**：只挂 `UIViewController` 自己。**子类自己重写且不调用
  `super`** 的 VC 我们看不到。这是刻意的取舍 —— 换成"挂所有子类"就是 2026-09-30 那次
  栈溢出闪退。Apple 明确要求 `viewDidAppear:` 调用 `super`，绝大多数实现都会调。
  漏掉的概率远小于"App 完全打不开"的代价。
- **崩溃定位的两条信息源分工**：`wf_crash.log` 独有的信息是**阶段标记**（崩在哪一步）；
  完整帧链以系统 `.ips` 为准（设置 → 隐私与安全性 → 分析与改进 → 分析数据）。
- **不碰网络层**：只做视图层和导航层，不 hook 任何请求/签名/鉴权逻辑。
- **H5 页面**：如果某页实际是 `WKWebView` 渲染的（实测「目的地」就是 React Native
  `RCTRootView`），原生视图树里只有一个宿主视图，隐藏要靠注入 CSS（v0.4）。
- **移除 tab 的副作用**：`selectedIndex` 会重映射（首次应用时把"停在被移除 tab"迁到
  `JT_DEFAULT_TAB_TAG`）；之后只在**越界**时才碰，避免把用户刚切到的 tab 拽回去。
- **v0.3 / v1.0 尚未覆盖的部分（不假装覆盖）**：
  - 开屏/启动弹窗的**类名还没有直接证据**。v0.3 用的是窄词表（`Splash` / `LaunchAd` /
    `Advertisement` / `AdViewController` …）+ 业务白名单。**如果启动弹窗没被收掉，是正常的** ——
    长按 JT 把诊断发回来，里面 `[弹窗] 弹出方 → 被弹方` 那一节就是它的类名，下一版直接补进去。
  - **`BannerCycleView` / `BannerCycleViewCell` 是推断出来的，不是实测**（推导见第 1 节）。
    装完请看一眼「电话/消息」页中部那条横幅是不是真的没了、有没有别的东西被误伤。
    误伤了就**长按 T** 立刻恢复，然后长按 JT 把诊断发我。
  - **粘性隐藏装不上的情形**：如果 App 的这几个类**自己实现**了 `layoutSubviews` 或 `setHidden:`，
    我们按规矩**不动它**，日志里会是 `[广告粘性·…] … App 自己实现，跳过`。
    那时粘性失效，只能退回定时扫掠（仍会在 ≤1s 内把广告藏回去，但用户可能看到闪一下）。
  - **收起（留白）已交给布局层（v1.1）**：`BannerCycleViewCell` / `TBMineBannerCell` 的高度
    由布局对象给，① ② ③ 改不动它，④ 只在自撑高布局下才被调用。v1.1 改走
    delegate 的 `collectionView:layout:sizeForItemAtIndexPath:` / `tableView:heightForRowAtIndexPath:`
    —— 那是 `prepareLayout` 的**输入**，改它才会真正重排。
    若日志里 `[广告item·自证]` 报"布局层没收到"且钩子调用次数为 0，说明我们猜错了宿主类
    （委托/数据源不是那个对象），把那一行发回来即可定位。
  - **残留的 section inset / 行间距空白：已接受，不再迭代**（Shawn 2026-09-30：不影响使用）。
    就算 item 已收到 0.5pt、与下一格仍有几 pt 空白，也不动 —— 动间距会波及整页所有格子，
    **代价不对称**（Gotcha 8：漏清只是少删一个广告，误伤是功能没了且极难查）。
  - **"记录 indexPath"不是"靠位置认身份"**：v0.3 那个自毁 bug 是**靠位置推断**；
    v1.1 是**记录真实 cell 报出的位置**并优先信任实时 cell，实时答案说"不是广告"就顺手删记录。
    详见第 6 节末尾那条说明。位置是**证据**，不是**身份**。
  - 广告扫掠只看**原生视图树**，管不到 H5/RN 里的广告（dump 里带 `[H5]` 标记的就是这类）。
  - App 若在 +30s 之后按服务端配置重建 tab bar，复检链已结束 —— 1 秒一次的定时器会兜住
    （调试版也可以点一下橙色 **T** 手动重收）。
  - **目标 ②（开屏/启动弹窗）至今零证据**：还没有一次会话真的弹过东西，无从判断。
    代码在（第 7 节），但**从未被触发过**，不敢说它可用。
